# Task 2 independent review

Verdict: changes requested. The implementation substantially improves the worker boundary, revision handling, cover diagnostics and update lock, but the lifecycle still permits incorrect chapter completion and loses pending reading evidence.

Scope: read-only inspection of the Task 2 brief, report, review diff, current tracking/content/background modules and adjacent storage/observer code. No product edits, commits or test reruns. Reported Vitest/typecheck results are implementation evidence, not independently rerun evidence. Task 1 backup changes and new manual workflow implementation are excluded.

## Findings

1. **P1 — Stop the old chapter tracker before detecting an SPA route.** `src/content/index.ts:178-180` changes the generation/report key but leaves `progress` and `currentChapter` alive. `run()` awaits a new observation at line 132; the old tracker keeps ticking during that await and during failed-observation retries. Its container callback at line 65 finds the new DOM after the old container is disconnected, and its paged callback at line 75 explicitly uses the new URL. A jump from unfinished Chapter 31 to Chapter 32 can therefore measure Chapter 32's restored end position as Chapter 31 and send a completion. The worker still has Chapter 31's state until the new observation installs state, and the same-origin check at `src/background/messages.ts:116` accepts this message. The client generation check protects observation acknowledgements only; it does not protect progress. Discard the old tracker immediately on route invalidation, cancel the old retry, and bind automatic evidence to the observation's route/document. Verify an in-flight/failed observation after a same-origin SPA jump cannot change Chapter 31's progress or completion.

2. **P2 — Final evidence is discarded on every pagehide.** `src/content/index.ts:184-187` sets `suspended = true` before calling `stopProgress()`. `ReaderProgress.stop()` flushes pending time/progress, but the sink at `index.ts:68` returns because `allowed()` excludes suspended pages. The tracker then clears its pending time. This affects ordinary navigation as well as BFCache: leaving after a five-second tick but before the ten-second send drops the pending five seconds, and an unfinished chapter's final progress event is never recorded. Flush permitted evidence before suspension, while continuing to discard on privacy revocation. Verify the integration with the real ReaderProgress class; the lifecycle test's mock stop cannot detect this ordering problem.

3. **P2 — BFCache shutdown can be undone by an already queued navigation callback.** `src/content/observer.ts:64` schedules `setTimeout(checkUrl, 50)` without retaining its timer; `stop()` does not cancel it or mark the watcher stopped. When this fires after `shutdown()` has called `watcher.stop()`, `checkUrl()` calls `ensureObserver()` and reattaches a MutationObserver before invoking the old callback. A later pageshow creates a second watcher because the content script set its watcher reference to null. Both watchers can then detect/mutate lifecycle state. Track/cancel the navigation timeout and make all observer callbacks no-op after stop. Verify pagehide between scheduling and execution leaves no active observer and pageshow creates exactly one watcher.

4. **P2 — A transient cover preflight storage failure poisons retries for the worker lifetime.** `src/background/covers.ts:51-54` performs `getSeries`, `getCoverStatus`, and `getCover` outside the try/finally at lines 60-72. If any rejects, the rejected promise remains in `inflight` and every later attempt for the same series/URL returns it without reading storage or fetching again. The automatic caller at `messages.ts:73` also discards this rejecting promise. Put the entire operation under cleanup and handle diagnostics-write failure without replacing the original recoverable outcome. Verify one rejected preflight read followed by a healthy retry performs a new attempt and does not leave an unhandled rejection.

5. **P2 — Revocation during the boundary's awaits can still write automatic evidence.** `src/background/messages.ts:109-118` reads settings before asynchronous tab-state and chapter reads. The progress handler then reads settings again at line 130 but uses only its completion threshold; it does not recheck the incognito/ignored-host rules before `recordProgress`. If access is revoked between the first read and that second read, the second settings object explicitly contains the revocation yet the write proceeds. Observation similarly reads permission settings before awaiting `takeExpectation` and storage persistence, and next-click completion trusts the earlier check. Client shutdown does not cancel messages already in the worker. Recheck authorization at the final write boundary, using a settings generation/serialization if needed to define the revocation ordering. Verify a deferred tab-state/chapter read with a settings revocation during the await rejects the write.

## Compliance and quality that hold under inspection

- Observation hostname derives from a validated URL rather than the supplied hostname. Main-frame/tab checks and bound series/chapter checks reject the basic spoofing cases; current host/incognito settings are consulted.
- Storage compares progress revisions inside the IndexedDB transaction. Content reconciles revisions and suppresses re-completion at an old end position until the reader moves below the threshold.
- Observation acknowledgement commits the report key only after success; retries are bounded and shutdown clears its tracked retry timer. Route changes do not explicitly cancel that timer yet (covered by finding 1).
- ReaderProgress cancels its own queued measurement, avoids counting time in hidden/unfocused/outside-reader states, and can restart after stop. Its standalone behavior does not establish the content script's final-flush correctness.
- Cover diagnostics persist locally, failed/pending attempts have bounded retry intervals, manual retry bypasses backoff, and ready status checks for a real cached Blob. Cache clearing removes detected references so revisiting can request reconstruction.
- The update checker sets an in-process guard before its first await, retains the durable expiring lease, refreshes it between sources, excludes removed sources and releases the guard in a nested finally. No concrete concurrent-acquisition defect remains in the inspected worker flow.
- No new backend, analytics, remote scripts/fonts, or external logging were introduced in this scope.

The reported tests cover representative success paths but do not exercise the cross-module route/pagehide ordering or failures before the cover operation's try block. Add targeted regressions for these findings; broader repeated test runs are unnecessary until fixes are made.

## Final-fix re-review

Read-only inspection confirms the five originally reported defects are addressed: route-bound canMeasure/sinks and immediate tracker stop prevent new DOM from becoming old evidence; pagehide flush precedes suspension; observers retain/cancel navigation timers and enforce stopped state; cover preflight reads now share cleanup; final authorization rereads and guarded mutations roll back mid-operation revocation. The reported 30 targeted tests were not rerun.

One narrow remaining boundary issue: `src/storage/db.ts` checks shouldWrite immediately after the callback, then awaits `done` without checking or aborting on subsequent policy changes. `src/background/messages.ts`'s policy listener only changes latestPolicy/policyEpoch. A revocation delivered after the final check but before IndexedDB's completion event can therefore leave the transaction committed. If the guarantee is rejection for every revocation delivered before commit, active guarded transactions must subscribe to policy invalidation and abort while still active. The present code provides a final-mutation fence, not an atomic Chrome-settings/IndexedDB commit. This is narrower than the original TOCTOU, and should be stated accurately or closed with an active-transaction abort mechanism.

### Commit-fence follow-up

Inspected the added active guarded-write registry in db.ts and policy listener integration in messages.ts. Revocation now aborts disallowed transactions while they await commit, and rollback maps aborted callbacks to WriteRevokedError. Completion/abort/error handlers remove registry entries. The added write-fence regression specifically exercises revocation after the final guard check. This closes the narrow remaining caveat above. Task 2 verdict after these fixes: approved under code inspection; reported tests were not rerun and browser behavior remains outside this review's evidence.
